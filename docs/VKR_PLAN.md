# РАЗДЕЛ B. РАБОЧИЙ ЖУРНАЛ И ТЕХНИЧЕСКАЯ СТРАТЕГИЯ

## 1. Текущая точка проекта

Проект уже содержит рабочий прототип для нагрузки WordCount:

- Docker/Spark/HiBench окружение описано в `docker-compose.yml`.
- Сбор WordCount датасета реализован старыми скриптами `archive/legacy_scripts/run_wordcount_experiments.sh` и `archive/legacy_scripts/collect_wordcount_data.sh`.
- Актуальный сборщик — generic `scripts/run_hibench_experiments.sh` + `scripts/collect_hibench_data.sh`.
- Текущий основной датасет: `data/wc_train_merged.csv`.
- Размер датасета: 401 успешная строка.
- Покрытые топологии:
  - 2 workers x 4 cores x 8 GB: 134 строки;
  - 3 workers x 3 cores x 6 GB: 133 строки;
  - 4 workers x 2 cores x 4 GB: 134 строки.
- Покрытый размер входных данных: только `profile=large`.
- Обученные модели и отчеты:
  - baseline ML: `out/final_best/baseline/report.json`;
  - DNN: `out/final_best/dnn/report.json`;
  - RL-оптимизация: `out/rl_topo336_constrained/report.json`.
- Текущий API: `api/main.py`; умеет предсказывать время для одной RF+SA модели по одной схеме WordCount.

Лучший текущий baseline на WordCount:

- `RandomForest_SimulatedAnnealing`: MAE 0.746s, RMSE 1.215s, R2 0.961, MAPE 3.19%.
- `RandomForest_RandomSearch`: MAE 0.815s, RMSE 1.189s, R2 0.963, MAPE 3.58%.
- DNN заметно хуже на тесте: MAE 3.037s, RMSE 3.949s, R2 0.591, MAPE 13.18%.

Главное ограничение текущего состояния: модель обучена только на WordCount, только на `large`, без явного признака `job_type`. Поэтому она не может корректно обобщаться на PageRank, K-Means, TeraSort и разные размеры данных.

## 4. План формирования датасетов

### 4.1. Нагрузки

Базовый набор:

- WordCount: уже есть, но лучше перегенерировать в новой единой схеме.
- KMeans: итеративная ML-нагрузка, чувствительная к CPU, памяти и повторяющимся Spark stage.
- K-Means: ML-нагрузка, чувствительная к CPU, памяти и числу итераций.
- TeraSort или Sort: shuffle-heavy нагрузка, полезна для проверки сетевых и shuffle параметров.

Если TeraSort в текущем HiBench образе окажется слишком тяжелым или нестабильным, допустимая замена для ВКР: Sort из HiBench micro workloads. В отчете важно явно объяснить причину замены.

### 4.2. Размеры данных

Для каждой нагрузки желательно минимум 3 размера:

- `small`;
- `large`;
- `huge` или `medium`, если `huge` слишком долго работает на доступной машине.

Один размер данных недостаточен: модель не сможет честно отвечать пользователю на параметр "размер данных".

### 4.3. Топологии

Минимально полезная матрица:

- 2 workers x 4 cores x 8 GB;
- 3 workers x 3 cores x 6 GB;
- 4 workers x 2 cores x 4 GB;
- 4 workers x 4 cores x 8 GB;
- 6 workers x 2 cores x 4 GB.

Если машина позволит, добавить:

- 6 workers x 4 cores x 8 GB;
- 8 workers x 2 cores x 4 GB.

Важно: топологии должны различаться не только общим числом ядер, но и формой кластера. Например, 2x8 и 4x4 могут иметь одинаковые суммарные ядра, но разные накладные расходы планирования и shuffle.

### 4.4. Количество экспериментов

Практичный минимум:

- 4 нагрузки x 3 размера x 5 топологий x 80 конфигураций = 4800 строк;
- 3 повтора на конфигурацию = 14400 фактических запусков.

Более качественный вариант:

- 4 нагрузки x 3 размера x 6 топологий x 120 конфигураций = 8640 строк;
- 3-5 повторов на конфигурацию.

Для ВКР лучше иметь меньше, но чище: физически валидные конфигурации, фиксированные версии Spark/HiBench, повторяемые prepare/run шаги и сохраненные логи ошибок.

## 5. Как генерировать конфигурации Spark

Случайная генерация текущего скрипта полезна, но ее надо сделать управляемой:

1. Сначала отфильтровывать физически невозможные конфигурации:
   - `executor_cores <= topology_worker_cores`;
   - `executor_memory <= worker_memory - reserve`;
   - `executor_instances <= workers * floor(worker_cores / executor_cores)` с учетом памяти;
   - `driver_memory` не должен вытеснять executors.
2. Использовать смешанную стратегию:
   - 20% default/near-default конфигурации;
   - 50% Latin Hypercube или stratified random по пространству параметров;
   - 20% конфигурации вокруг лучших найденных областей;
   - 10% стрессовые крайние значения.
3. Сохранять seed генерации для воспроизводимости.
4. Не удалять failed runs: они полезны как сведения о невалидных областях, но для регрессии времени использовать только успешные строки.

## 7. Изменения в ML пайплайне

### 7.1. Препроцессинг

В `models/data.py` нужно добавить:

- `job_type` как категориальный признак;
- числовой `input_size_bytes`;
- опционально `input_records`;
- поддержку единого multi-workload CSV;
- групповые split-правила, чтобы тест не был слишком похож на train.

Рекомендуемые split-сценарии:

- обычный random split для общей метрики;
- holdout по топологии: проверка обобщения на новую топологию;
- holdout по размеру данных: проверка обобщения на другой масштаб;
- holdout по workload не делать основным, потому что предсказывать совершенно новую нагрузку без данных почти всегда некорректно.

### 7.2. Модели прогнозирования времени

Сравнить минимум:

- Dummy/median baseline;
- LinearRegression или Ridge;
- RandomForest;
- ExtraTrees;
- Gradient Boosting / HistGradientBoosting;
- SVR;
- MLP sklearn;
- DNN PyTorch.

Если будут доступны зависимости и время:

- XGBoost/LightGBM/CatBoost как сильные табличные модели.

Метрики:

- MAE;
- RMSE;
- R2;
- MAPE;
- per-workload MAE/MAPE;
- per-profile MAE/MAPE;
- per-topology MAE/MAPE.

### 7.3. Поиск оптимальных конфигураций

Нужно разделить две задачи:

1. `PerformancePredictor`: модель предсказывает время для заданной конфигурации.
2. `ConfigOptimizer`: алгоритм ищет конфигурацию, минимизирующую предсказанное время.

Сравнить оптимизаторы:

- grid/random search по допустимой области;
- simulated annealing;
- Bayesian optimization;
- Q-Learning/DQN/PPO как исследовательская часть по статье.

В отчете важно честно указать: RL/BO оптимизируют surrogate model, поэтому обязательно нужна реальная валидация лучших конфигураций на Spark.

## 9. Реальная проверка predicted vs actual

Для каждой нагрузки и размера:

1. Взять default конфигурацию.
2. Взять лучшие рекомендации нескольких оптимизаторов.
3. Запустить каждую конфигурацию 3-5 раз.
4. Сохранить:
   - predicted time;
   - actual median time;
   - absolute error;
   - percentage error;
   - actual speedup vs default;
   - predicted speedup vs default.

Минимальный validation set:

- 4 нагрузки x 3 размера x 2 топологии x 5 конфигураций = 120 проверочных строк.

Именно этот этап должен подтвердить, что рекомендации не только хорошо выглядят в модели, но и работают на реальном Spark.

## 14. Уточнение стратегии после обсуждения

Дата уточнения: 2026-04-24.

### 14.1. Что меняется в приоритетах

Сравнение уже реализованных моделей не является первостепенной задачей. Текущие RF/DNN/RL реализации нужно воспринимать как прототип, а не как зафиксированную архитектуру.

Новая главная цель: подобрать более валидную постановку задачи и входные признаки, чтобы рекомендации конфигураций подтверждались на реальных Spark job, а не только на тестовом split датасета.

Рабочая декомпозиция:

1. Сначала строим качественный датасет и проверяем, какие входные признаки реально нужны.
2. Потом обучаем несколько надежных предикторов времени.
3. Затем поверх лучших предикторов запускаем оптимизаторы конфигураций.
4. В конце подтверждаем рекомендации реальными запусками Spark.

Иными словами, модель из статьи не должна диктовать архитектуру. Статья остается ориентиром для набора Spark-параметров и идеи RL/поиска, но не ограничивает нас в выборе более подходящего подхода.

### 14.2. Выбор трех нагрузок

Для ограничения в 2 суток лучше сфокусироваться на 3 нагрузках, а не на 4. Рекомендуемый набор:

- WordCount;
- PageRank;
- Sort или TeraSort.

Обоснование различий:

- WordCount: простая map/reduce нагрузка с умеренным shuffle. Хороша как базовая проверка пайплайна, потому что она понятна, стабильна и уже частично исследована в проекте.
- PageRank: итеративная графовая нагрузка. Сильнее зависит от памяти, числа итераций, shuffle между итерациями и стабильности executor'ов. Хорошо показывает, как конфигурация Spark влияет на повторяющиеся стадии.
- Sort/TeraSort: shuffle-heavy нагрузка. Основной интерес в сортировке и передаче данных между executors, поэтому здесь особенно важны shuffle buffer, compression, maxSizeInFlight, число executors и память.

Если TeraSort окажется слишком дорогим по времени, берем HiBench Sort. Для отчета формулировка: TeraSort является более тяжелым вариантом shuffle/sort workload; в условиях ограниченного экспериментального бюджета был выбран Sort как более воспроизводимая нагрузка той же природы.

K-Means можно оставить как резерв или дополнительную нагрузку, если после пилота останется время. Он полезен как ML workload, но при лимите 2 суток важнее покрыть три кардинально разные модели поведения: простая агрегация, итеративный граф, тяжелый shuffle.

### 14.3. Ресурсы и топологии

Так как реальных ресурсов будет меньше, чем в статье, лучше не пытаться повторять масштаб авторов. Вместо этого нужно честно спроектировать компактный, но разнообразный кластерный эксперимент.

Желательная машина для комфортного сбора:

- CPU: 16-32 физических/логических ядер;
- RAM: 64-128 GB;
- диск: SSD/NVMe, желательно с запасом 200+ GB;
- ОС: Linux;
- запуск через Docker, как в текущем проекте.

Минимально допустимый вариант:

- CPU: 12-16 ядер;
- RAM: 48-64 GB;
- SSD;
- меньше топологий и меньше повторов.

Важно: параллельно собирать несколько Spark workload на одной физической машине нежелательно, если мы измеряем время выполнения. Параллельные Spark job будут конкурировать за CPU, память, диск и сеть Docker, а датасет получится загрязненным. Параллелить можно только на независимых машинах или если каждому эксперименту выделены жестко изолированные ресурсы. На одной машине лучше запускать последовательно, но автоматизированно.

### 14.4. Экспериментальный бюджет на 2 суток

Цель: получить не максимальный, а достаточно качественный датасет, который позволяет обучить предикторы и проверить рекомендации.

Стартовая матрица для 2 суток:

- 3 нагрузки: WordCount, PageRank, Sort/TeraSort;
- 2 размера данных: `small` и `large`;
- 4 топологии;
- 50-70 уникальных конфигураций на каждую ячейку `job_type x profile x topology`;
- 3 повтора на конфигурацию.

Расчет строк:

- 3 x 2 x 4 x 60 = 1440 строк датасета;
- 1440 x 3 = 4320 фактических Spark запусков.

Если средний запуск занимает 20-40 секунд, это укладывается примерно в 24-48 часов с накладными расходами. Если PageRank или TeraSort окажутся тяжелее, уменьшаем `SAMPLES_PER_CELL` для тяжелых нагрузок, но сохраняем баланс по топологиям и размерам.

Адаптивный вариант:

- WordCount: 70 конфигураций на ячейку;
- PageRank: 50 конфигураций на ячейку;
- Sort/TeraSort: 40-50 конфигураций на ячейку;
- validation-запуски лучших конфигураций вынести отдельно после обучения.

### 14.5. Почему текущий WordCount мог не подтвердиться

Потенциальные причины, которые нужно проверить в новом пайплайне:

- train/test split был случайным внутри тех же топологий и конфигурационного пространства, поэтому метрики могли быть оптимистичными;
- модель предсказывала время, а RL выбирал минимум по surrogate model, что может приводить к exploitation ошибок модели;
- пространство конфигураций включало физически слабые или неравномерно покрытые области;
- `profile` был только `large`, поэтому модель не видела масштаб входных данных;
- не сохранялась полная статистика повторов и разброс времени;
- реальные validation-запуски могли выполняться в условиях, отличающихся от сбора обучающего датасета;
- часть параметров Spark могла не применяться так, как ожидалось, если HiBench/Spark конфиг перезаписывался или игнорировался;
- Docker workers на одной машине имитируют кластер, но не дают полной сетевой картины реального многомашинного Spark.

В новом сборе нужно обязательно сохранять примененный `spark.conf`, логи запуска и summary Spark/HiBench по каждому эксперименту или хотя бы по каждому батчу.

### 14.6. Более валидная постановка ML-задачи

Нужно отказаться от идеи "модель напрямую предсказывает конфигурацию" как основной. Более контролируемая схема:

1. Модель `f(job_type, input_size, topology, spark_config) -> runtime`.
2. Оптимизатор перебирает или генерирует допустимые `spark_config`.
3. Лучшие кандидаты проверяются реальным Spark запуском.

Так мы можем:

- сравнивать предикторы времени отдельно;
- сравнивать оптимизаторы отдельно;
- объяснять пользователю, почему выбрана конфигурация;
- показывать несколько рекомендаций в веб-интерфейсе.

Кандидаты на предикторы:

- ExtraTrees/RandomForest как сильный базовый уровень для табличных данных;
- HistGradientBoosting или XGBoost/LightGBM/CatBoost, если зависимости доступны;
- Gaussian Process или Quantile Regression для оценки неопределенности на малом датасете;
- DNN только как дополнительный эксперимент, если датасет станет достаточно большим.

Кандидаты на оптимизацию:

- constrained random search как честный baseline;
- Bayesian optimization;
- simulated annealing;
- evolutionary search;
- RL оставить как исследовательский вариант, если он будет подтверждаться real-run validation.

### 14.7. Какие входные данные нужны веб-сервису

Минимальный вход для точного предсказания:

```json
{
  "job_type": "wordcount",
  "input_size_bytes": 1073741824,
  "input_profile": "large",
  "topology": {
    "workers": 4,
    "worker_cores": 4,
    "worker_memory_gb": 8
  },
  "constraints": {
    "max_executor_cores": 4,
    "max_executor_memory_mb": 6144,

```

Для конкретного `/predict` дополнительно передается полный `spark_config`. Для `/recommend` сервис сам генерирует кандидатов `spark_config` внутри допустимой области.

Желательные дополнительные признаки:

- число записей или строк во входе, если HiBench может это достоверно дать;
- число итераций для PageRank/K-Means, если оно фиксируется конфигом;
- Spark version;
- режим запуска: standalone/yarn/local;
- число partitions/shuffle partitions, если мы решим включить это в оптимизируемые параметры.

### 14.8. Что должен показывать веб-интерфейс

Веб-интерфейс должен показывать не одну конфигурацию, а несколько лучших рекомендаций:

- подход/model;
- optimizer;
- predicted runtime;
- expected speedup vs default;
- recommended Spark config;
- предупреждения по ресурсам;
- confidence/uncertainty или хотя бы пометку "внутри/вне области обучающего датасета";
- если есть validation: actual runtime и ошибка прогноза.

На выходе после экспериментов выбираем 2-3 лучших подхода и именно их интегрируем в UI/API.

## 15. Облачная машина, входные данные сервиса и качество датасета

Дата уточнения: 2026-04-24.

### 15.1. Рекомендуемые ресурсы облачной VM

Текущий docker-compose поднимает HDFS, YARN, Spark master, Spark history server, HiBench, MLflow и динамические Spark workers. Для корректного сбора датасета важнее стабильность и изоляция ресурсов, чем попытка повторить масштаб статьи.

Рекомендуемый вариант для одной машины:

- CPU: 24-32 vCPU;
- RAM: 96-128 GB;
- Disk: 300-500 GB SSD/NVMe;
- OS: Linux;
- Docker Engine + Docker Compose plugin;
- swap: лучше выключить или держать минимальным, чтобы Spark не уходил в медленный swap.

Минимально допустимый вариант:

- CPU: 16 vCPU;
- RAM: 64 GB;
- Disk: 200-300 GB SSD;
- меньше топологий, меньше профилей или меньше конфигураций на ячейку.

Комфортный вариант:

- CPU: 32 vCPU;
- RAM: 128 GB;
- Disk: 500 GB NVMe.

Почему нужен запас RAM:

- часть памяти съедают постоянные сервисы Hadoop/Spark/HiBench/MLflow;
- Spark workers должны получать заявленную память без вытеснения;
- PageRank и Sort/TeraSort могут создавать заметный shuffle и временные данные;
- при нехватке памяти измерения становятся нестабильными или начинаются failures, которые портят датасет.

### 15.2. Одна машина или две

На одной физической VM не стоит одновременно собирать два Spark датасета. Даже если контейнеры разные, они делят CPU, RAM, диск, Docker network и I/O. Время выполнения job перестает отражать только Spark-конфигурацию и начинает отражать конкуренцию с соседним экспериментом.

Правильные варианты:

1. Одна мощная VM: все Spark experiments идут последовательно; обучение моделей запускается только если оно не мешает сбору или в паузах.
2. Две VM: каждая собирает независимую часть датасета, например VM1 = WordCount/PageRank, VM2 = Sort/TeraSort.
3. Одна VM для сбора, вторая меньшая VM для обучения и анализа уже собранных CSV.

Если бюджет позволяет, лучший практический вариант:

- VM для сбора: 24-32 vCPU, 96-128 GB RAM;
- VM для обучения/анализа: 8-16 vCPU, 32-64 GB RAM.

Если хочется ускорить именно сбор, можно взять две одинаковые VM меньшего размера:

- 2 x 16 vCPU, 64 GB RAM, 250-300 GB SSD.

Но при объединении датасетов нужно зафиксировать одинаковые Docker images, версии Spark/Hadoop/HiBench, scripts commit, workload profiles, генератор конфигураций и schema version.

### 15.3. Можно ли обучать PageRank, пока собираются другие нагрузки

Можно, если обучение идет на другой машине или хотя бы не конкурирует с активным Spark сбором. На одной VM это рискованно:

- RF/ExtraTrees/Boosting могут активно грузить CPU;
- DNN может грузить CPU/GPU;
- параллельное обучение изменит фоновые задержки Spark job;
- итоговые runtime в датасете станут менее чистыми.

Компромисс: собрали PageRank batch, скопировали CSV, обучаем на локальной машине или второй VM, пока первая VM последовательно собирает следующую нагрузку.

### 15.4. Два размера данных: достаточно или нет

Для пилота достаточно `small` и `large`: они позволяют быстро проверить, запускаются ли workloads и есть ли различие во времени.

Для финальной рекомендательной системы два размера данных являются слабым покрытием. Если пользователь вводит произвольный размер данных, модель с двумя точками масштаба плохо понимает форму зависимости runtime от размера входа.

Рекомендация:

- пилот: `small`, `large`;
- финальный сбор: минимум 3 размера, например `small`, `medium`, `large`;
- если `medium` в HiBench профилях недоступен или неудобен, использовать `small`, `large`, `huge` только для тех workloads, где `huge` укладывается во время;
- если остаются только два размера, UI/API должны явно ограничивать пользователя выбором `small` или `large`, а не обещать точность для произвольного размера.

Правильный входной признак: не только `profile`, но и числовой `input_size_bytes`. `profile` удобен человеку, но модель должна видеть численный масштаб.

### 15.6. Чего не хватает текущему WordCount датасету

Текущий датасет уже полезен, но для стабильной предсказательной системы в нем не хватает:

- `job_type`;
- `input_size_bytes`;
- `input_records`;
- всех длительностей отдельных повторов: `run_1_duration_s`, `run_2_duration_s`, ...;
- `mean_duration_s`;
- `std_duration_s`;
- `min_duration_s`;
- `max_duration_s`;
- `iqr_duration_s`;
- `cv_duration = std / mean`;
- `successful_runs`;
- `failed_runs`;
- `error_type`;
- `experiment_id`;
- `timestamp`;
- `schema_version`;
- `script_version` или git commit;
- сохраненного примененного `spark.conf` или hash конфигурации;
- признака cold/warm run, если первый запуск после prepare заметно отличается.

Для обучения основной target лучше оставить `median_duration_s`, но строки с большим разбросом повторов помечать:

- если `cv_duration > 0.15-0.20`, строку считать нестабильной;
- можно не удалять ее сразу, но использовать меньший sample weight или вынести в анализ выбросов;
- если успешных повторов меньше минимального порога, строку не использовать в train regression.

### 15.7. Сколько повторов нужно

3 повтора:

- подходят для пилота;
- позволяют быстро оценить, запускается ли workload и насколько грубо отличается runtime;
- плохо защищают от случайного выброса.

5 повторов:

- хороший компромисс для финального сбора при лимите 2 суток;
- медиана устойчивее, чем при 3;
- время сбора растет умеренно.

9 повторов:

- ближе к статье;
- лучше для финальной валидации и отдельных контрольных конфигураций;
- слишком дорого для полного датасета в нашем лимите.

Рекомендация:

- pilot: 3 повтора;

## 16. Краткий план ближайших действий

Дата уточнения: 2026-04-24.

### 16.1. Ресурсы первой облачной машины

Если хотим покрыть весь диапазон Spark-параметров из текущего проекта и статьи в духе `executor_cores=1-8`, `executor_instances=1-8`, `executor_memory=1-8g`, то машина должна выдерживать максимальную конфигурацию:

- 8 executors x 8 cores = 64 executor cores;
- 8 executors x 8 GB = 64 GB executor memory;
- driver до 4 cores и 4 GB;
- Hadoop/Spark/HiBench/OS overhead.

Практичная рекомендация для первой VM:

- CPU: 64 vCPU;
- RAM: 128 GB;
- Disk: 500 GB SSD/NVMe;
- OS: Linux;
- Docker Engine + Docker Compose plugin.

Это не повторяет масштаб статьи, но позволяет честно тестировать верхнюю границу нашего пространства параметров без постоянной нехватки ресурсов.

Если бюджет ограничен, рабочий компромисс:

- CPU: 32 vCPU;
- RAM: 128 GB;
- Disk: 500 GB SSD/NVMe.

Но тогда верхнюю границу `executor_instances=8` и `executor_cores=8` вместе использовать нельзя: в генераторе конфигураций нужно ограничивать суммарные executor cores.

### 16.2. Вход сервиса: исправленная постановка

Пользователь не должен вводить HiBench-профиль `small/medium/large`. Это внутренняя экспериментальная шкала для сбора данных.

Пользователь должен вводить:

- тип нагрузки: например `wordcount`, `pagerank`, `sort`;
- примерный размер входного датасета: bytes/GB;
- доступные системные ресурсы;
- опциональные ограничения.

Минимальный вход:

```json

  "input_size_gb": 7,
  "resources": {
    "total_cores": 64,
    "total_memory_gb": 128,
    "disk_available_gb": 500
  }
}
```

Расширенный вход:

```json

  "job_type": "pagerank",
  "input_size_gb": 7,

    "total_cores": 64,
```

Если пользователь не знает разбивку по workers, модель может работать по агрегированным ресурсам. Но для Spark Standalone/YARN точнее иметь и агрегированные ресурсы, и форму кластера. Поэтому в датасете лучше хранить оба вида признаков:

- `total_cores`;
- `total_memory_gb`;
- `nodes/workers`;
- `worker_cores`;
- `worker_memory_gb`.

В UI можно показывать простую форму, а расширенные поля сделать опциональными.

## 17. Актуальная стратегия сбора датасета (2026-04-24, финальная)

### 17.1. Итоговые решения

После проверки параметров на 64 vCPU / 128 GB VM и сверки с Table 1 из Sensors22 (статья `sensors-22-05930-v2.pdf`):

- Grid параметров Spark в `collect_hibench_data.sh` — **идентичен Sensors22 Table 1** (16 параметров, те же диапазоны и шаги).
- 3 нагрузки — достаточно: **WordCount, TeraSort, PageRank**. KMeans — опционально, собирается позже.
- Профили — только `small` и `large`: `huge` выходит за бюджет времени, `medium` сломан в HiBench image.
- Порядок сбора: **TeraSort → PageRank → WordCount** (опционально KMeans). TeraSort первой, потому что это быстрая shuffle-heavy нагрузка — первый usable датасет получим за ~2 суток и начнём обучение ещё до того, как соберутся остальные.

### 17.2. Топологии (6 штук)

| # | workers × cores × mem | Σ cores | Σ mem | Зачем |
|---|---|---|---|---|
| T1 | 2 × 4 × 8 GB | 8 | 16 | минимальный baseline |
| T2 | 4 × 4 × 8 GB | 16 | 32 | сбалансированный небольшой |
| T3 | 4 × 8 × 16 GB | 32 | 64 | широкий executor при 32 cores |
| T4 | 8 × 4 × 8 GB | 32 | 64 | много узких воркеров, same Σcores |
| T5 | 6 × 6 × 12 GB | 36 | 72 | средний размер |
| T6 | 8 × 6 × 12 GB | 48 | 96 | потолок в рамках 64 vCPU |

T3 и T4 оба дают 32 cores, но разной формы — это даёт модели возможность разделить эффект "мало широких executor-ов" vs "много узких". T6 = 48 cores; выше нельзя без overcommit против постоянных контейнеров (namenode, datanode, YARN, spark-master и т.д. резервируют ~8–15 cores в пике). Старый вариант `8×8×8` = 64 cores упирался в физический потолок машины и добавлял бы шум во времена прогонов.

### 17.3. Матрица и параметры сбора

Одинаково для всех трёх нагрузок:

- `PROFILES=small,large`;
- `TARGET_SAMPLES=80` уникальных конфигов на ячейку (6 топологий × 2 профиля × 80 = **960 конфигов на нагрузку**);
- `REPEATS=3` (median + cv_duration, шумные строки отсекаются при обучении по `cv > 0.25`);
- `MAX_TOTAL_EXECUTOR_CORES=48, MAX_TOTAL_EXECUTOR_MEMORY_GB=90` — физические лимиты VM.

Почему `REPEATS=3`, а не 5: для регрессии времени выполнения **разнообразие конфигов важнее глубины повторов**, если CV повторов умеренный. 3 повтора дают стабильную медиану и позволяют высвободить время на больше уникальных конфигов. Переход 5→3 — минус 40% времени, которые конвертируются в +60% уникальных конфигов (с 50 до 80 на ячейку).

Итого на каждую нагрузку: 6 × 2 × 80 × 3 = **2880 реальных Spark-запусков**.

### 17.4. Ожидаемое время

По данным smoke-прогона и оценке large по сравнению с small:

| Workload | avg small | avg large | Per-workload time |
|---|---|---|---|
| WordCount | ~15 s | ~75 s | ~36 ч ≈ 1.5 сут |
| TeraSort | ~25 s | ~100 s | ~48 ч ≈ **2 сут** |
| PageRank | ~30 s | ~240 s | ~112 ч ≈ 4.7 сут |

Суммарно (последовательно на одной VM): ~8.5 суток для всех трёх нагрузок. KMeans добавляется отдельно ещё на ~2 суток.

Первый usable датасет (TeraSort) — примерно на 2-е сутки от старта сбора, что позволяет начать обучение и итерации на предикторе/оптимизаторе, пока собираются PageRank и WordCount.

### 17.6. Чего ещё не хватает (подтянуть в первую итерацию до большого запуска)

Критичные фиксы уже в репо (см. `docs/DATASET_COLLECTION_STATUS.md`). Оставшиеся улучшения для качества датасета:

1. `INPUT_HDFS_PATH` для PageRank сейчас указывает на `/Pagerank/Input/edges`. Надо брать родителя `/Pagerank/Input`, чтобы `du -s` считал edges+vertices, а не только edges.
2. Запись `error_type` в CSV при failed runs: tail `bench.log`, классификация по keyword (OOM / timeout / AM killed / Java exception). Сейчас только `exit_code`.
3. Добавить `--cpus="$c" --memory="${m}g"` в `docker run` для Spark worker-ов в `run_hibench_experiments.sh`. Без этого Docker физически не изолирует CPU/RAM, и worker-ы могут конкурировать с постоянными контейнерами за ресурсы, шумя во времена.
4. Seed RNG записывать в CSV для воспроизводимости (сейчас случайный pick по `$RANDOM`).
5. Сохранять applied `spark.conf` и последние строки `bench.log` рядом с CSV-строкой (сейчас только `spark_conf_hash`).

Эти 5 пунктов — вторая волна фиксов перед запуском полного сбора. Без них датасет будет работать, но будет содержать меньше диагностической информации.

### 17.7. Вход сервиса: финальная постановка

Пользователь рекомендательного сервиса **НЕ вводит** ни HiBench-профиль (`small/large`), ни конкретный `spark.conf`. Он вводит **свои системные ресурсы и характеристики задачи**:

- тип задачи (`job_type`: wordcount/pagerank/terasort/kmeans);
- размер входного датасета в байтах или GB;
- доступные системные ресурсы: total_cores, total_memory_gb, disk, опционально nodes;
- ограничения (max_executor_cores/memory/instances) и предпочтения (top_k, optimize_for).

Сервис сам генерирует кандидатов `spark.conf` в рамках ограничений, прогоняет их через предиктор времени, ранжирует по runtime/speedup и возвращает top-K с warning-ами для потенциально невалидных конфигураций.

Это **отличается** от старой схемы из `plan_practice.txt`, где пользователь якобы передавал топологию и размер в GB напрямую. В финальной схеме топология (workers × cores × mem) выводится из ресурсов и ограничений автоматически или передаётся как расширенный параметр.
